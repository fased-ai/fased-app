# Ubuntu releases

Fased uses saved GitHub authentication and automated build attestations. Customers install a compiled package through one entry and use Settings → Update or the installed `fased update`. They need no Go compiler, Node, source checkout or release-signing password.

The selected candidate, installed identities, active checkout, results and exact action authority live in Current (`/home/fc/fasedbot/docs/fased/execution.md`, active checkpoint) in the workspace implementation record. Preserve its original Local PASS within that package's scope. Changes to candidate bytes require matching affected installed evidence; this guide never grants delivery, publication or activation authority.

The protected workflow produces authenticated Local proof. Actual persistent Remote evidence is separately reviewed under the owner-selected GitHub contract below. Current records completed and missing legs; the publisher refuses missing or incomplete evidence.

## Status and authority

This is the controlling staged-package acceptance contract for Fased App. Current owns the active outcome and permissions. The contract requires complete Local acceptance before any VPS test, mandatory Tailscale before Remote deployment, and one password-free routine UI/CLI updater. Prior receipts retain only their original scope. The producer, installed-acceptance consumer and publisher consume the same exact package evidence; code and focused checks alone are insufficient. Mining and live AI/wallet/trading remain disabled. Automatic updating is an explicit user choice, tested against controlled releases with Manual restored afterward.

Installation acceptance and publication readiness have separate exits. B01 closes when the reviewed admission code is integrated, the completed matching Local/fresh/upgrade evidence is recorded through the approved owner review, and the publisher's read-only acceptance verifier consumes it. Reuse accepted artifacts and journeys; do not replace or reenroll an accepted persistent node, repeat an unchanged accepted leg or create a diagnostic version. A genuinely missing fresh/package-bound leg needs its explicitly authorized clean disposable environment; preserve the accepted instances and original baselines. Publication additionally requires the installed Provider → Agent → Chat → Task → Result → optional Memory journey and applicable publication authority. A closed B01 does not claim that agent acceptance or public distribution is complete.

The release command must require the trusted workflow’s matching Local installed-acceptance artifact and the exact owner-reviewed Remote record before creating a tag or publishing. If any required leg is absent or failed, promotion stops. Current records the actual verification status; no release is ready merely because this contract is documented. Existing published releases and trust profiles remain immutable.

## One candidate, one acceptance flow

| Stage                | Required result                                                                                                                                                                                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Review source        | Finish one connected correction, focused checks, protected PR and required CI. Merge only within recorded authority. Ordinary PRs and merges create no tag.                                                                                                                   |
| Stage once           | Freeze the reviewed source commit/tree and one proposed version. An authorized run of the existing protected Ubuntu workflow builds and attests one unpublished candidate from that commit, without a release tag. Retain its artifacts and digests.                          |
| Accept the package   | Complete the actual released-predecessor Local UI and CLI journeys first; only after Local PASS exercise mandatory-Tailscale Remote using that same candidate. Record exact inputs and every required result. A failed or missing leg holds promotion.                        |
| Promote once         | Check the acceptance record against the exact source, workflow/run/attempt and artifact digests. Create the annotated tag at the accepted commit only after PASS. Publish the retained artifacts without rebuilding, recompiling, repacking or rerendering accepted payloads. |
| Confirm distribution | Verify real immutable GitHub release/asset identities, attestations and anonymous download digests. Then perform any authorized existing-owner update through the normal product entry. Public readback confirms distribution; it cannot replace installed acceptance.        |

The candidate identity is the source commit/tree, proposed version, platform, workflow identity, run ID/actual attempt and artifact inventory digests. Preserve that identity in the existing candidate directory and publisher journal. Changing relevant bytes or inputs creates a new unpublished candidate under the same proposed version and invalidates affected evidence. No duplicate full journey before and after a tag is required. A tag does not rebuild the candidate.

Acceptance-consumer corrections do not require replacing unchanged shipping bytes. After reviewed integration, dispatch this same workflow with `source` set to the reviewed consumer main commit and both `candidate_run` and `candidate_attempt` set to the original producer. Empty paired inputs select the normal build; incomplete, noncanonical or repeated replay inputs fail. Replay skips the build, authenticates the original successful producer/provenance step, verifies the original artifact ZIP digest and bounded regular-file inventory, then executes the existing installed journey. Preserve the original package source/tree/run/attempt; the consumer commit and acceptance run are separate evidence identities.

The Local receipt remains the strict one-file authenticated artifact. Agent receipt and observations are retained separately for the existing package/Local-hash-bound owner review. The verifier discovers replay proof by the original producer identity and requires exactly one successful protected-main attempt1 with installed acceptance PASS and build SKIPPED. Failed-parent artifacts cannot substitute for proof or hide one subsequent successful result; multiple successful results refuse ambiguity. Consumer repair and replay never create a release, tag or activation permission.

## Staged acquisition and trust boundary

Use the existing candidate verifier, controlled transport fixtures, packaged installer, wizard and update controller. Extend those facilities only where the joined route is missing. No new service, trust system or customer setup command is required.

- Acquire the candidate from the exact authenticated CI artifact and verify its inventory and original attestation before executing it. - Adapt the existing provenance policy explicitly for protected, commit-bound staging. At promotion, bind the final annotated tag to that same accepted commit and original artifact provenance. Preserve strict verification for existing tag-bound profiles. Never relabel a workflow event, forge an attempt or relax repository/workflow/source checks to make a candidate pass.
- The controlled acceptance harness supplies staged release discovery/download responses at the existing acquisition boundary. It runs the packaged entry, verifier, wizard, authentication and installation/update controller with the retained executable/package bytes. Only the external delivery responses differ. Record this as controlled staged acceptance, not proof of a public immutable release. - Controlled transport responses stay confined to disposable acceptance state. An explicitly authorized existing host may instead use the separately compiled maintainer admission, pinned to its exact attested packet, operation and protected installation baseline; require reviewed delivery and the same candidate's complete Local PASS first. This is not an ordinary product channel or customer setup option. Customer acquisition still rejects drafts, mutable/unattested artifacts and arbitrary endpoints; no runtime source, CA or trust switch is added. Actual host acceptance must record that admission route honestly. Only the matching installed job/receipt and required real-host results establish their respective scopes; source/preflight PASS cannot substitute.
- Release/asset IDs created during promotion belong in publication receipts and journals. Every executable, archive, embedded UI and customer entry script accepted by digest must be published unchanged. ## Complete packaged journey

Use the existing explicitly authorized Local environment. An Ubuntu Local VM proves that profile/OS, not native Fedora/macOS/Windows acceptance. ### Gate 1 — complete Local first

1. Install/run the supported ACTUAL released predecessor as an ordinary Local user. Use its packaged UI and ordinary owner access. No new human OS account, separate default Fased password, supplied token, copied claim code or hidden CLI login may complete the UI scenario.
2. From Settings, check/review/apply the candidate through the installed updater. Verify installed version/identity, meaningful data/drafts/authentication, signer/recovery holds and service health. Repeat Update → Already current. Observe explicit failures rather than supplying generic prompt answers that mask unwanted password/terminal steps.
3. From the same approved predecessor baseline, use installed `fased update`. UI and CLI must select the same release policy and use the SAME authorization rules, controller, journal, result and recovery. Inspect a UI-started operation in CLI and a CLI-started operation in UI; preserve the same operation identity, never double-apply concurrent requests. Local/host CLI authorization is kernel/OS-owner proof through protected IPC. A Remote client CLI uses its approved owner/device connection over Tailscale HTTPS without SSH or another core. Neither copies browser cookies or asks for an app/root/sudo password.
4. Exercise affected cancellation/interruption/recovery boundaries. Preserve keys/data/uncertain holds and the owner's stopped/paused intent. The maintenance controller must remain recoverable while the core is being replaced; no terminal helper can stand in for UI recovery acceptance.
5. Opt into bounded Automatic mode on the authorized disposable profile. Close the browser and any setup/control SSH session, prove actual apply/restart/result with no interactive credential request, then restore Manual. Browser logout is not revocation of an explicitly saved software-update policy. It grants no wallet unlock, permission expansion or task/trade replay.
6. Source regressions and required policy-selected CI precede the authorized reviewed-main candidate build. Installed Local acceptance follows that build and gates Remote. Do not repeat unchanged CI after Local or repeat passed Local for unchanged bytes; refresh only proof invalidated by a correction. Any required Local FAIL stops Remote/VPS testing and promotion.

### Gate 2 — Remote only after Local PASS

1. Start the literal official one-command entry once from initial SSH/provider console. Root performs trusted OS/Tailscale preparation only; all Fased executables run after privilege drop. Preserve TTY and environment boundaries.
2. Verify Tailscale installation, enrollment, the intended tailnet and the accessing owner's private reachability BEFORE Fased payload deployment, database creation, app/signer services or wallet setup. Only prerequisite OS/Tailscale/administrator preparation may precede this gate. Refusal/failure/noninteractive missing proof stops installation. No SSH-only fallback, skip flag or direct-binary bypass completes Remote.
3. Reuse an existing non-root administrator where possible. A root-only host needs an owner-approved public-key recovery administrator; no empty password or automatic copying of every root key. The private key stays on the client. Verify actual key-only private login and independent console/rescue before disabling root/password SSH. Do not erase an existing administrator's credentials. App and signer identities are locked/non-login, without sudo or SSH keys. Any human administrator's approved sudo policy is separate from service permissions.
4. Install verified Fased into its confined service, bind its HTTP backend to loopback/protected local transport, configure private HTTPS without public Funnel, and bind the exact owner AND trusted device through the protected private handoff and validated Tailscale identity; new devices need owner approval, not automatic takeover from network membership. Negative tests must reject other tailnet users/shared devices, missing/forged proxy headers, untrusted local callers, CSRF and identity takeover. Local owner sessions have equivalent UID/launcher/Origin protections. Do not remove old authentication until the replacement is explicitly enrolled and accepted.
5. Reuse the existing five-minute network transaction: preserve foreign policy; prove fresh private UI and independent recovery; stage owned firewall/SSH changes; verify NEW public SSH/web/backend connections fail over IPv4/IPv6 while NEW allowed private connections work; confirm/persist. No existing established SSH socket counts as proof. Failure, reboot or timeout must preserve/recover access and leave setup incomplete. No silent public fallback. Reject unreviewed shared-host disruption.
6. Close the bootstrap SSH connection, preserving unrelated owner sessions. From direct Tailscale HTTPS—not an SSH forward—repeat owner access, UI AND installed-CLI update/recovery/result parity, restart, Already current, data/auth preservation, actual reboot/reconnect and controlled Automatic operation. No ongoing browser/SSH session or password handoff may be a dependency. Root/account/key setup is not repeated for ordinary Update.

## Recovery and tag discipline

- Reuse a valid candidate and its original provenance when resuming publication. Inspect the journal and remote release/asset state before mutation. A timeout after a write requires readback, not blind recreation.
- One proven transient pre-artifact infrastructure failure may receive one bounded same-source retry with its real attempt. The conductor must bind the actual successful attempt; falsified attempt identity is refused and recovery does not consume a new version.
- A failed candidate stays unpublished and untagged. Correct the cause, run affected checks and replace only invalidated evidence. Preserve useful original failure records.
- Never move/delete a release tag or replace published assets. If an exceptional source defect is found after tagging, hold publication. Changed source must pass the same gate before a later deliberate release; never create a chain of diagnostic tags.
- A publication failure resumes the accepted candidate without a rebuild. If its original artifacts or trusted acceptance evidence are unavailable, hold and record the missing input.
