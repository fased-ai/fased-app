# Installation and update contract

The [user installation guide](guide/install.md) describes the required Local/Remote experience. The [release acceptance guide](maintainers/ubuntu-release.md#complete-packaged-journey) defines its engineering gates. Current authority/status is `/home/fc/fasedbot/docs/fased/execution.md`.

Public0.1.11 now supplies the supported Ubuntu24.04/amd64 installation/update contract. Its original package passed recorded controlled Local/Remote/Tailscale/update acceptance and final public distribution readback; Current records exact evidence and held activation. Older0.1.6 behavior is historical compatibility context, not the target workflow. Do not replace UI-update acceptance with a customer-run helper command.

- **Local first:** actual installed supported public predecessor → protected owner session → UI and CLI through the same updater → preservation/restart/recovery/Already current → bounded Automatic operation. No new human OS account or default Fased password.
- **Remote prerequisite:** OS/Tailscale preparation is allowed first. Verified enrollment and private reachability are mandatory before Fased deployment, database initialization, services or wallet setup. Refusal/failure stops there; no SSH-only fallback or skip flag.
- **Private HTTPS setup:** the administrator installer handles the local Tailscale authorization needed for its owned Unix proxy. The app stays unprivileged. Setup preserves existing routes and stops on conflicts; interrupted writes resume from their saved ownership record rather than reset Tailscale. Accepted candidate evidence includes the corrected Serve/private-access journey. Use Current for the exact accepted package and pending public-delivery status; do not restart enrollment from a historical failure.
- **Remote completion:** verified owner/private HTTPS plus private administrator and independent console/rescue access → existing timed hardening transaction → public denial/private continuity → persist → close bootstrap SSH. Core and signer are unprivileged; no ongoing tunnel is needed.
- **Accounts:** reuse the Local OS user; Remote reuses or provisions a key-authenticated recovery administrator without an empty password. App/signer accounts are locked, non-login identities. Their users/passwords never become customer forms. Do not disable root SSH until a replacement administrator and recovery route work.
- **Updates:** Settings and installed `fased update` use one controller, release policy, journal, progress/result and recovery. UI uses the existing owner session; Local/host CLI uses authorized OS-owner/admin proof through protected IPC, while a Remote client CLI uses its approved owner/device connection over Tailscale HTTPS; Automatic uses saved scoped software-update authority. No session/cookie copying or generic password/sudo handoff. Initial OS approval or exceptional new privileges are separate setup actions.

Keep published assets immutable and existing data/credentials/recovery holds intact. A terminal repair is not a successful UI upgrade. Reuse the exact scoped predecessor, Local and existing-VPS evidence recorded in Current. Fresh Remote setup/update/closure and authenticated admission have retained accepted evidence for0.1.11. That exact0.1.11 package is now publicly delivered with final publisher/readback PASS. Do not repeat those tests merely because later Wallets work has separate acceptance gaps.

Independent provider console/rescue is required before public lockdown; private SSH over the same tailnet is not independent. Without it, do not declare the current Remote profile complete or silently open a public fallback. Before real-wallet use, portable encrypted backup and restore outside the original VPS/tailnet must pass B05. [Access-provider outage and recovery](guide/install.md#recovery-and-availability) separates these boundaries. Alternative access providers require their own accepted access and recovery path.
